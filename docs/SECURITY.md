# Security

For production configuration and release operations, use the [deployment guide](DEPLOYMENT.md) and [launch readiness checklist](LAUNCH_READINESS.md). Automated tests and source review reduce known risks but are not a penetration test or verification of production-provider configuration.

## Admin-managed public site content

The announcement and launch-video editor is available only inside the existing server-authorized Admin settings. Its write endpoint checks the request origin and administrator identity, streams at most 16 KiB of JSON, rejects unknown fields, validates schedule order and HTTPS destinations, and reports whether its admin audit-log write succeeded. React renders announcement copy as text; it does not interpret HTML or Markdown. Public GET responses include only content whose schedule is currently active. Supabase RLS is enabled on `site_content`, browser roles have no table grants, and the server-only service role performs reads/writes. Apply `20261111000000_ai_gateway_credits.sql` (which creates the admin audit table) and `20261117000000_site_content_controls.sql` before enabling the feature.

The video is loaded directly by the visitor's browser from the administrator-supplied public HTTPS URL; the app server does not fetch or proxy that URL. Admins must use a host that sends an appropriate `Access-Control-Allow-Origin` header for the app's `crossorigin="anonymous"` media element and COEP policy. Treat the URL as public, do not place tokens in it, and do not use the feature as an upload service. The external video host receives each viewer's request and may collect its own access data.

## Browser security headers

`src/proxy.ts` attaches a per-request nonce Content Security Policy to app and public responses and passes the nonce through request headers for the shared Next.js layout. Script policies use the nonce and `strict-dynamic`; no route allows the `'unsafe-eval'` or script `'unsafe-inline'` directives. The existing `wasm-unsafe-eval` allowance is scoped to browser lab screens that use WebAssembly. All routes retain `X-Frame-Options: DENY` and `frame-ancestors 'none'`. `next.config.ts` sets COOP/COEP for the browser features that require cross-origin isolation. The retired C runner route `/lab-runner/c` returns 404 and has no special CSP or framing exception.

## Credential handling

Developer credentials belong in ignored local `.env.local`: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, and `OPENROUTER_API_KEY`. Server-only provider adapters and API routes read them; client components do not read those environment values. They are not returned from `/api/status` or `/api/models`, written to application logs, or exposed through `NEXT_PUBLIC_` variables. Shared platform requests use server credentials and do not attach a provider key from the browser. Ollama has no cloud credential; its local address is separate workspace configuration.

In production deployments, `.env.local` is not deployed. Production secrets (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `SUPABASE_SERVICE_ROLE_KEY`, `GUEST_SESSION_SECRET`, `KATALYST_ADMIN_EMAILS`) must be configured securely in the deployment platform's server environment dashboard. `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is a public site key, not a secret; configure its matching private secret in Supabase Auth before enabling CAPTCHA protection. See [DEPLOYMENT.md](DEPLOYMENT.md) for detailed platform-specific configuration instructions and verification checklists.

Settings supports user-entered session keys for providers that allow BYOK. The learner selects **Save for this tab** before a value becomes active; **Clear session key** removes the active value and field draft. Active and unsaved values stay in React memory only; reload or close the tab clears them. In explicit BYOK mode, the browser sends that user-entered value in the `x-katalyst-provider-key` request header to the KATALYST server for model discovery and chat. The server necessarily receives it transiently to make the provider request. It is not put in a URL, localStorage, IndexedDB, chat records, analytics, or persistent server storage. Session keys are accepted only over HTTPS, except localhost/loopback for development. A session key takes precedence over the matching environment key only in explicit BYOK mode. No credential value is included in returned provider/model metadata.

Cloud model-discovery cache entries store only a SHA-256 digest in their cache key and normalized model metadata; they do not keep the raw session key. Results expire after five minutes, and callers can request refresh. Ollama model results are fetched fresh and are not cached. Environment credentials remain in server process configuration.

Session BYOK remains separate from account persistence. Keys entered in Settings stay in page memory for the current tab; they are never included in the local guest snapshot, account JSON, migration request, export, or database. Server environment provider credentials remain server-only. KATALYST does not store personal provider keys persistently and does not claim application-level encryption at rest.

Cloudflare Workers AI uses the account ID to build a fixed server-side API URL and the API token as a bearer credential. The account ID is not treated as a secret; the token is. A custom token needs Cloudflare Workers AI Read and Edit permissions. Shared Cloudflare credentials are used only by the server-side Kat AI gateway; the browser receives the public model ID for its model indicator but never the platform token/account ID. Shared requests are limited to Kat, and the selected shared model comes only from admin configuration (the request body's model is ignored). Workspace requests use a separate BYOK path; the user chooses a provider and may enter their own transient session credential. The public Cloudflare model catalog is unavailable in shared mode. A present environment value does not prove that discovery or inference is authorized. Cloudflare quota and paid usage depend on the account and model; the app's global daily credit cap does not set a Cloudflare dollar cap. See the [provider guide](AI_PROVIDER_GUIDE.md#cloudflare-workers-ai-default-hosted-provider) for current provider notes and official references.

## Threat model and deployment

Optional account routes support email/password and Google sign-in through Supabase Auth and enforce per-user account data ownership. One `/login` page handles sign-in, account creation, password recovery, and Google OAuth. Email sign-in/account creation require an acceptance checkbox; Google opens a separate confirmation dialog. The server signs the current Terms and Privacy versions into a short-lived HttpOnly cookie, requires it at the OAuth callback, and stores the first acceptance per user/version in `legal_consent_records`. The migration `20261118000000_legal_consent_records.sql` is applied to the connected Supabase project; verify it on each additional target before enabling account auth. The record contains version IDs, acceptance time, and method, not the full legal text or a claim of identity verification. Optional Turnstile challenges protect email sign-in, registration, and password reset only when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and the matching Supabase Auth secret are configured; Google OAuth relies on Supabase/provider controls. This ledger, CAPTCHA, and UI gate do not replace deployment-specific legal review or Supabase Auth rate limits. The AI gateway enforces per-account or signed-guest request limits, per-user/guest credits, and an atomic admin-configured global daily shared-use cap. This credit cap is not an upstream Cloudflare dollar-spend limit. The app also does not provide global IP reputation or bot defense; public deployments still need suitable edge/WAF controls, monitoring, and provider billing alerts. A guest's signed cookie is the credit identity. Separately, a trusted proxy address is HMAC-hashed for a 120-request-per-minute guest network burst limit; visitors behind the same network share that burst limit but never share a guest credit balance. Vercel uses its platform-owned `x-vercel-forwarded-for` address and ignores client-supplied forwarding headers. Other proxy deployments must configure a trusted client-IP header; if none is available, this separate network limit is skipped rather than trusting a caller-controlled header. The default development and production start scripts bind to `127.0.0.1`.

Session-key requests require HTTPS in production; deploy behind TLS and ensure the application request URL reflects HTTPS. Local HTTP is allowed for loopback development. The app does not rely on forwarded-protocol headers for this check.

## Account identity and cloud data

Google OAuth uses Supabase Auth's PKCE flow through `@supabase/ssr`; email/password uses Supabase Auth's password flow. The Next.js 16 `src/proxy.ts` refreshes cookie sessions; the OAuth callback exchanges the authorization code. The proxy is not an authorization boundary. Every account API route calls Supabase `auth.getUser()` on the server and derives the user ID from that verified result. Account mutation routes also require a same-origin `Origin` header.

The SQL migration creates `profiles`, `account_snapshots`, and an internal `guest_migrations` ledger. Profile and snapshot tables have RLS enabled and grant only the operations they use. Their policies require both `auth.uid()` ownership and a live JWT `session_id` row in `auth.sessions`. The live-session check means a revoked or deleted Auth session cannot continue reading the snapshot with an otherwise unexpired stateless JWT. The revision/migration RPC is SECURITY DEFINER only to perform one atomic compare-and-save; it accepts no user ID, derives `auth.uid()`, checks the live session, and always scopes its row and migration record to that owner. The ordinary snapshot read uses the user's session and RLS. `guest_migrations` has no direct client grants.

Workspace, projects, conversations, messages, skills, provider/model preferences, learning progress, and appearance preferences are stored in one validated JSON snapshot row with its owning `user_id`. Nested workspace records inherit the aggregate row's owner. Request bodies use the existing workspace/progress/preference validators and a 9 MB aggregate limit. Snapshot writes compare an expected revision; stale writes return a conflict and do not replace the current row. The browser keeps the original local keys and syncs a local mirror. Cross-device changes are pulled only when the local copy matches its last synced digest; otherwise the UI asks the user to restore the cloud copy or merge the device copy.

Guest migration is explicit. Before migration or account replacement, KATALYST stores a validated guest snapshot in `katalyst.guest-backup.v1` on that device. A migration ID is persisted locally before the request and recorded atomically with the server snapshot, so retries of an uncertain request are idempotent. Existing workspace IDs are retained where possible and collisions are remapped by the established workspace merge. Learning completions are unioned by stable course/lesson IDs, activity is deduplicated and capped, and the user chooses which appearance preference to keep. The source guest backup remains until the user clears browser data; sign-out and account deletion restore it. A full browser quota can prevent migration; in that case the server is not changed by the UI and the user should export/free local storage first.

The account export endpoint returns the authenticated user's workspace, progress, and preferences as a private no-store download, with no provider session keys. Account deletion requires typing a confirmation phrase, recent authentication (within 10 minutes), and a database-backed limit of three attempts per account per 15-minute window. It uses the server-only `SUPABASE_SERVICE_ROLE_KEY` after verifying the current user and calls Auth's permanent delete API. Apply `20261118030000_account_action_rate_limits.sql` for the shared, atomic deletion throttle; the endpoint fails closed in production when its required database control is unavailable. The Auth foreign-key cascade removes the profile, account snapshot, consent record, migration ledger rows, and action-limit record. Account data is removed from active tables immediately; Supabase-managed database backups may retain deleted rows according to the project's plan and retention settings, which KATALYST cannot change or promise to erase early. The RLS session check blocks the deleted user's revoked session even during the remaining lifetime of a JWT. The local guest backup is restored and remains on the device. Review Supabase's current [user deletion guidance](https://supabase.com/docs/guides/auth/managing-user-data) and [backup retention](https://supabase.com/docs/guides/platform/backups) for project-specific retention behavior.

## AI Gateway, Quotas, and Abuse Prevention (M15)

KATALYST gates all shared inference behind a centralized server-side gateway (`src/lib/ai-gateway/gateway.ts`). No client can directly invoke shared Cloudflare Workers AI credentials without passing through server-side authorization, rate limits, kill-switch checks, atomic credit reservation, and ledger logging.

Key security controls:
1. **Server-Side Credential Boundary**: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` remain strictly server-side and are never sent to browser bundles or client API responses.
2. **Quota & Balance Authoritativeness**: Client-supplied balances, user IDs, or model weights are never trusted. All credit balances, monthly allowances, and deduction calculations are evaluated in PostgreSQL transactions with row-level locks (`SELECT ... FOR UPDATE`), preventing race-condition overspending.
3. **Guest Abuse & Identity Defense**: Unregistered guests receive server-issued, tamper-resistant HMAC-SHA256 signed session cookies; the signed guest ID is the primary credit and per-user rate-limit identity. A separate 120-request-per-minute network burst limit uses an HMAC-SHA256 digest of a trusted proxy address. It is intentionally generous and shared by visitors behind the same public IP; it does not merge their credit balances. Vercel uses its platform-owned `x-vercel-forwarded-for` header. A production deployment behind another proxy must configure which proxy header is trusted. If no trusted address exists, the IP burst limit is skipped rather than trusting a user-supplied forwarding chain. These are abuse controls, not guarantees against VPNs, botnets, deliberate cookie deletion, or shared networks. The application-wide daily shared-use cap limits aggregate exposure if a guest clears their cookie. Guest session and credit records expire and are pruned in bounded batches.
4. **Emergency Kill Switch & Policy Limits**: Administrators can instantly pause all shared AI inference via an audited kill switch. Shared and BYOK chat requests use configured one-minute request limits (15 req/min for authenticated users, 6 req/min for guests by default). With Supabase configured, a service-role-only PostgreSQL RPC applies the counter atomically across app instances; identities are stored as SHA-256 digests. The `ai_request_rate_limits` table has no client grants or RLS policies for browser users.
5. **BYOK Boundary Isolation**: BYOK requests (Gemini, OpenAI, OpenRouter, and Ollama) are handled in an isolated branch and count against the request-rate limit. BYOK calls do not deduct KATALYST credits, and failed BYOK requests never fall back to Cloudflare.
6. **Brevo Transactional Integrity**: Brevo transactional email credentials (`BREVO_API_KEY`) are server-only. Email dispatch runs asynchronously and is non-blocking; external email failures never disrupt authentication or inference.

The shared request limiter is installed by `20261116000000_ai_request_rate_limits.sql`; the atomic global shared-AI daily credit budget is installed by `20261118010000_ai_global_daily_budget.sql`. All eight repository migrations are recorded on connected project `wcnoxasohsqscovomnms`. Its 18 public tables have RLS enabled, stored function bodies match the repository migration sources, and rollback-scoped SQL assertions passed for the guest-session, global-budget, account-action, and server-only credit RPC paths. The repository pgTAP suite was not run because pgTAP is not installed on that project and the Supabase CLI is unavailable in this checkout. Recheck any separate target before enabling chat; a configured database that cannot apply the limiter/budget fails closed instead of silently reverting to a process-local counter. Local development without service credentials uses in-memory fallbacks, which are not suitable for multi-instance production. A global daily credit limit is an application quota, not an upstream Cloudflare billing cap.

The pre-fix database logs contained 2,260 SQLSTATE `42702` ambiguous-column errors from PostgREST guest-session RPC calls in the reviewed 24-hour window. The hardened guest-session function matches the repository source, and no PostgreSQL ERROR entries appeared in the checked window after it was applied. Current Supabase advisors still report leaked-password protection disabled, three authenticated SECURITY DEFINER RPCs used for session/admin checks and owner-scoped snapshot writes, RLS without policies on tables that have no browser-role grants, five unindexed foreign keys, and three unused indexes. Enable leaked-password protection in Supabase Auth and review the performance findings before public launch. The security advisor's function notices do not by themselves mean those owner-scoped RPCs are unsafe; their authorization checks and grants remain part of the review.

## Request validation and provider boundary

The chat API validates provider and model IDs, message roles, history count, per-message size, workspace-context size, aggregate text size, and request body size. The model-list API limits upstream payloads and paginated Cloudflare/Gemini catalogs. OpenAI, Gemini, and OpenRouter calls have a 45-second timeout; Cloudflare Workers AI uses 60 seconds. Cloud catalog calls have a 20-second timeout. Ollama discovery has an 8-second timeout and generation a 120-second timeout. Redirects are rejected. Authentication, permission, account/API, quota, invalid model/response, timeout, and network errors are normalized without returning raw credentials or provider payloads. Raw authorization headers and prompt contents are not logged by KATALYST.

Cloud adapters contact fixed official HTTPS endpoints. Custom OpenAI-compatible URLs are not supported. Blocking only `localhost` strings is not enough: safe custom endpoints need DNS resolution and IP pinning, private/link-local/metadata address rejection, redirect enforcement, and outbound network controls to prevent DNS rebinding and SSRF. The current app does not provide those guarantees, so arbitrary base URLs are intentionally not accepted.

Ollama is a local-only exception. Its address is restricted to `localhost`, `127.0.0.1`, or `[::1]` on port `11434`, with no URL credentials, path, query, or fragment; redirects are rejected. Both Ollama API routes require the incoming KATALYST host to be loopback and, when an `Origin` header is present, reject it unless it exactly matches the local request origin. Default scripts bind KATALYST to `127.0.0.1`; non-loopback deployments cannot use Ollama through these routes. This boundary is not an authentication system and does not make an unauthenticated KATALYST deployment safe: keep KATALYST local, do not override the loopback bind, bind Ollama only to its local interface, and do not expose port 11434 or tunnel it to the internet. Localhost is a network boundary choice, not a claim that local HTTP is encrypted.

OpenAI requests set `store: false`. Gemini and OpenRouter requests use their official APIs and server-side authentication. Cloudflare catalog discovery validates the account catalog but does not prove generation access. Settings provides a separate manual Cloudflare **Test inference** action that sends a minimal prompt to the selected catalog model and may consume account quota. It is never run automatically. Ollama uses its local `GET /api/tags` and non-streaming `POST /api/chat` endpoints; KATALYST does not manage or download models. These request options do not replace reviewing provider-specific data processing, retention, billing, and API terms. A model catalog entry is not proof of account access.

## Code execution sandboxing and security boundary (M17.3)

KATALYST provides local browser workbenches and interactive simulators. Python runs in Pyodide WebAssembly, JavaScript runs in a Web Worker, SQL uses in-memory SQLite WebAssembly, and HTML/CSS renders in a sandboxed iframe. Arduino/ESP32 and circuit lessons use browser-side simulators.

In-browser C compilation and execution is provided via a client-side WebAssembly toolchain (`binji/wasm-clang` + `wasm-ld` + in-memory MemFS with a custom WASI preview-1 runner), gated behind `NEXT_PUBLIC_C_RUN_ENABLED` (default `false` until operator rollout). C++ remains disabled pending complete lesson matrix verification.

Key security controls for in-browser C execution:
1. **Zero External Inference/Execution APIs**: Compilation and execution execute 100% inside the learner's browser. No learner source code, standard input, or runtime output is sent to any server or external API.
2. **Zero Eval / Script Nonce Hardening**: No code path uses `eval()` or `new Function()`. The strict per-request nonce CSP remains intact without script `'unsafe-eval'` or `'unsafe-inline'`. WebAssembly compilation uses `'wasm-unsafe-eval'` exclusively on lesson and playground routes.
3. **Dual-Worker Isolation**: Compilation runs in `compiler-worker.js` and user code executes in a separate ephemeral `execution-worker.js`. If a user program crashes or traps, the compiler worker and app thread remain unharmed.
4. **Memory and Resource Limits**: Linker flags cap user WebAssembly linear memory at 32 MB (`--max-memory=33554432`) with a 1 MB stack. Out-of-bounds access or excessive heap allocations trap safely without crashing the tab. Output is capped at 64 KB and execution has a strict 10-second wall-clock timeout.
5. **Virtual In-Memory Filesystem**: The WASI shim provides a sandboxed in-memory file table (`files` Map). File I/O (`fopen`, `fprintf`, `fclose`) operates entirely in ephemeral memory with zero access to the host disk or network.
6. **User Abort Control**: A Stop button immediately terminates the active execution worker without restarting the compiler worker.
7. **Prebuild Integrity Verification**: Toolchain binaries are not stored in Git. `scripts/download-c-toolchain.mjs` verifies SHA-256 checksums at prebuild time; any mismatch aborts the build.

Execution for all local browser workbenches does not upload source to the KATALYST server. When a learner explicitly asks Kat to explain code, the bounded source and relevant lesson context may be sent to the selected AI provider as untrusted reference data. Imported skills do not run code.

## Assistant response rendering

Model output is untrusted content. Assistant Markdown is parsed into React elements with `react-markdown`; KATALYST does not enable raw HTML parsing or `dangerouslySetInnerHTML`. Raw HTML is skipped, only HTTP(S), `mailto:`, and in-page fragment links are rendered, external links use `noopener noreferrer`, and Markdown images are omitted so a response cannot cause an image fetch. Highlighted code is displayed as text; its copy button only writes that code to the clipboard and never runs it. These rules apply equally to OpenAI, Gemini, OpenRouter, and Ollama output. User messages retain the existing plain-text renderer.

## Imported skills and prompt injection

Imported Markdown instructions are untrusted data. The importer bounds file size and metadata, validates required fields, removes control and bidirectional formatting characters, and replaces embedded `<script>` blocks. The interface renders text through React escaping; no skill code executes, and no references or scripts are resolved.

The skill record retains source filename and optional HTTPS source URL, version, author, declared license, compatibility labels, installation date, and additional metadata. Credentials are discarded from metadata fields with recognized credential names. Source licenses are never inferred: absent license data is shown as not provided. Compatibility labels are declarations and do not establish behavior in KATALYST or another agent.

Only enabled, non-duplicate skill instructions enter a bounded prompt. Project and skill text is JSON-encoded and added to the latest user message, never placed in the trusted system/developer instruction field. Fixed provider instructions say to treat workspace context as untrusted and not honor requests there to reveal secrets or override trusted rules. The API key is not included in that context. Prompt boundaries reduce risk but cannot guarantee that a model will disregard malicious text. Inspect skills before enabling them and do not include secrets in their instructions.

Each chat request also carries a schema-limited assistant surface (`workspace` or `kat`). Trusted provider instructions include the app-selected provider and exact model ID; the OpenRouter free route is identified as routing whose upstream model may vary. This is request provenance, not proof of the model's internal identity or capabilities. Kat replies show the provider/model used for that individual response, even if the user later changes their selection. KATALYST has no browsing, filesystem, external-account, arbitrary tool, or code-execution integration in chat. These instructions and labels cannot force a provider model to obey them; outputs remain untrusted and must not be represented as verified actions.

Skill Issue discovery opens the public catalog for manual review. M4 review found no documented machine-readable API, so KATALYST does not scrape it or auto-fetch catalog content. Users inspect upstream source/license details and import Markdown explicitly. Downloaded skill files are text only; no scripts execute.

## Workspace backup and restore

The version-1 workspace backup is a user-triggered local download; it remains separate from account synchronization. Strict Zod schemas accept workspace, project, and conversation formats only. Unknown credential or authorization properties are rejected; application provider keys and transient session keys are outside the exported workspace shape. The optional loopback Ollama address is ordinary workspace configuration and may be included. Credential-like metadata fields are discarded, and common provider-key patterns, bearer values, and labeled key/token/password assignments are redacted from exported text. This pattern-based redaction cannot recognize every arbitrary secret in free-form conversation or instruction text, so users should inspect a backup before sharing it. Signed-in accounts also have a separate server-generated account export containing workspace, learning progress, and appearance preferences.

Restore checks the file size, version, schemas, duplicate IDs, and imported skills before committing. Merge is the default and remaps conflicting IDs; replace is available only for a full workspace and requires confirmation. KATALYST prepares the complete next record first and writes localStorage once. A validation, size, or storage failure leaves the prior storage value intact. Browser storage may have a lower quota than the 8 MB file limit. Unsupported backup versions are rejected; future schema changes need an explicit migration before acceptance. A malicious backup cannot add unknown executable properties or run code, but imported instructions remain untrusted prompt text and can influence a model if enabled.

Local startup validates existing raw `katalyst.workspace.v1` data and accepts older v1 records without the Ollama model preference. It does not automatically migrate the record to a new envelope or storage engine. Corrupt, unsupported, or inaccessible records are held out of the normal save path. If some entries validate, KATALYST offers a salvage action; it downloads the original raw record before replacing it. For records that cannot be salvaged, a confirmed fresh-workspace action also initiates an original-record download before writing. A failed write leaves the prior value in localStorage. Browser localStorage is synchronous and commonly has a 5 MiB per-origin limit, so a large workspace may hit quota before the app's 8 MB bound. IndexedDB migration is deferred until there is a tested dual-read and rollback plan.

## Local data and reporting

In guest mode, projects, conversations, provider choice, model choice, the local Ollama address, pinned state, and imported skills are stored in browser localStorage without KATALYST-managed encryption or server sync. For an account after the user explicitly chooses migration, a validated snapshot of workspace and conversations is also stored in the user's RLS-protected account row. Theme/text density and learning progress remain separate versioned browser records and are included in the account snapshot after sign-in. AI activity remains local. Session keys are excluded from all local and cloud structured records. Cloud provider prompts and context are sent to the selected third-party model service. Ollama prompts are sent to the local Ollama server on the KATALYST host. Do not enter sensitive content unless you accept those local-storage, account-provider, and model-processing boundaries.

Usage values are displayed only when a provider response reports them. Ollama token counts are local inference metadata and are not cloud charges. Cost is shown only when OpenRouter returns a valid cost value; KATALYST does not calculate provider cost from token counts.

AI activity stores at most 500 request events and contains only provider ID, model ID, timestamp, outcome, and input/output token counts explicitly returned by the provider. It excludes prompt/response text, API keys, headers, and estimated cost. It is best-effort: a storage problem does not prevent an AI request. Analytics are local, are not in workspace backups, and are not sent to a telemetry service.

Conversation **Share / export** creates a local Markdown download with the title and visible conversation messages. It excludes project instructions, skill content, provider/model settings, and other workspace metadata. Recognizable credential patterns in transcript text are redacted. Pattern redaction cannot detect every secret in arbitrary prose; review a transcript before sharing it. No public share URL is created.

Appearance preferences are a separate, strict, size-bounded record containing only the selected theme (`light`, `dark`, or `system`) and text density (`comfortable` or `compact`). They are included in the account snapshot after an explicit account choice. Corrupt or unsupported preference and activity records are preserved and surfaced as local data issues rather than silently overwritten.

## Learning progress and tutor requests

Learning progress is stored separately in browser localStorage under `katalyst.learning.v1` and remains outside the version-1 workspace backup. It contains path enrollment, lesson IDs, timestamps, and bounded learning activity; it contains no provider credentials or tutor turns. The Progress dashboard can export this validated version-1 record as a separate JSON file for guest or signed-in use without changing the local storage schema. After an explicit account migration choice, the same validated progress record is included in account snapshots and account exports. The record is size-limited and validated against known curriculum IDs. Corrupt or unsupported versions are left untouched and block account migration until resolved.

Kat sends a learner's message and, when launched from a lesson, lesson text/objectives/exercise to the selected provider using the established `/api/chat` protections. In the integrated lesson, an explicit code-help action may also send the current editor source (at most 7,000 characters), recent diagnostics (2,000 characters), and program output (2,000 characters). Editing, compiling, and running code alone does not send it. Lesson, source, diagnostics, and output are user-level untrusted context, not trusted system rules; the provider may process them under its own terms. Tutor conversations stay in page memory but still leave the browser when the learner sends a cloud provider request. No answer changes progress automatically. The four tutor modes are prompts, not behavioral guarantees. Do not include secrets in a question or imported lesson material.

## C and C++ editor status

C and C++ lessons, CodeMirror editors, and local versioned drafts under `katalyst.c.playground.v1` and `katalyst.cpp.playground.v1` remain available. Both Run buttons are disabled and show the friendly upgrade message. The `NEXT_PUBLIC_C_RUN_ENABLED` flag remains fail-closed, but setting it cannot restore execution because the runtime implementation and `/lab-runner/c` route have been removed. The decision followed repeated production compile timeouts; the c2wasm spike was also rejected for low curriculum coverage, unsupported core C features, unclear licensing, and missing diagnostics. The previous source state is recoverable from git tag `c-runtime-archive` at commit `509c0a9`.

Only when a learner explicitly asks Kat for code help can bounded editor source and lesson context be sent to the selected provider. Editing or reading C/C++ code alone makes no network request. No execution provider or C/C++ compile API currently receives the drafts.

### Compiler Sandboxing and Remote Execution Boundaries (M16)

KATALYST establishes strict security boundaries for multi-language and simulation execution:
1. **Client-Side First**: Python, JavaScript, SQL, and HTML/CSS use browser WebAssembly, Web Workers, or sandboxed iframes. C/C++ execution is retired; their editor drafts are local and no user code is executed on the Next.js server.
2. **Cloudflare Workers AI Boundary**: Cloudflare Workers AI is used strictly for AI inference, not for arbitrary general-purpose compiler execution. Workers AI has no POSIX runtime or isolated Linux execution environments.
3. **Remote Sandbox Requirements**: When remote runners (e.g., Piston or Judge0 microVMs) are integrated for heavy runtimes like Java OpenJDK:
   - Remote runners must operate in dedicated, isolated container/microVM environments.
   - All network egress must be disabled (`network: none`).
   - Strict resource limits must be enforced: CPU time (<= 8s), compile time (<= 15s), memory (<= 128 MB), output size (<= 64 KB).
   - Remote sandboxes must have zero access to application databases, secrets, or internal networks.
   - Filesystems must be temporary and wiped immediately after execution.
   - Requests must be rate-limited and credit-metered through the AI Gateway.
   - Do not deploy an unsafe general-purpose execution service merely to achieve server-side compilation.

See [COMPILER_ARCHITECTURE.md](COMPILER_ARCHITECTURE.md) for full architectural evaluations and risk analysis.

Do not open a public issue containing an exploit or secret. Contact the maintainers privately through the repository's security reporting channel once a remote repository is established. Remove real credentials and user data from any report.
