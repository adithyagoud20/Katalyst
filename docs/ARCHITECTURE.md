# Architecture

## Overview

KATALYST is a Next.js App Router technical learning studio with a published multi-discipline course catalog, a separate progress domain, and a secondary AI workspace. Guest mode remains local-first. Optional email/password or Google identity and account snapshot persistence use Supabase Auth/Postgres behind server-verified route handlers; provider calls continue through isolated adapters.

```text
Browser UI
  ├── localStorage: existing workspace + separate learning, preference, and AI activity records
  ├── page memory: session API keys and transient Kat tutor turns
  ├── Supabase browser Auth client: email/password, Google OAuth PKCE, and cookie session
  ├── GET /api/status: readiness booleans + initial configuration
  ├── GET /api/models: provider catalog, discovered using env/session credentials
  ├── POST /api/chat: validated provider/model/messages/context/assistant surface
  │     ├── ModelProvider contract: normalized text + optional provider usage
  │     │     ├── Cloudflare Workers AI Chat Completions API (default hosted provider)
  │     │     ├── OpenAI Responses API
  │     │     ├── Gemini generateContent API
  │     │     ├── OpenRouter Chat Completions API
  │     │     └── Ollama local chat API
  │     └── cloud provider key from server environment or transient request header
  ├── /auth/callback and /api/account/*: verified account, snapshot, export, deletion
  └── Supabase Postgres: profile + one revisioned, RLS-owned account snapshot per user
```

## Module boundaries

- `src/components/workspace.tsx` owns the shell, provider/model controls, session-key inputs, skill UI, conversation actions, and storage recovery UI.
- `src/components/learning-experience.tsx` renders the published course catalog into the learning navigation surfaces, integrated lesson workspace, practice, progress view, and local progress hydration. Course selection and lesson presentation use the catalog schema rather than course-specific UI. A C course conditionally exposes the C workbench; a course without that subject keeps a two-panel lesson/Kat layout. Lessons use a 27/43/30 learning, code, Kat panel grid on wide layouts and accessible Learn/Code/Kat tabs at 1200px and below. Lesson context, editor state, and Kat stay mounted together; the selected tab changes visibility without changing routes. `src/components/kat-tutor.tsx` sends bounded, provider-independent course and lesson context through the existing chat request when the learner asks Kat.
- `src/components/c-playground.tsx` hosts the CodeMirror C11 editor and existing Wasmer browser compiler. Entering a lesson starts compiler setup in the background; the package cache is reused, progress is displayed, and failure exposes retry while the lesson remains usable. Run is enabled after setup. Compilation, diagnostics, stdin, output limits, stop handling, network-disabled sandbox execution, and local drafts remain in this component. `scripts/copy-wasmer-browser-runtime.mjs` copies the SDK runtime assets to `public/vendor/wasmer-sdk` before dev/build so its worker modules load from same-origin static paths.
- `src/lib/c-playground.ts` owns the versioned local draft record, size bounds, lesson-code extraction/wrapping, and compiler/runtime constants.
- `src/lib/learning-navigation.ts` serializes the selected workspace section and optional lesson ID into the URL fragment and safely restores it from browser history.
- `src/lib/learning-curriculum.ts` contains a Zod-validated subject/course catalog, authored course outcomes, ordered modules and lessons, objectives, prerequisites, C11 examples, optional `LearningExampleRun` sample input, expected output and bounded expected-file records, exercises, and separate checkpoints. The current thirteen runnable C lessons all have an expected run. These records describe reference results; loading a lesson does not compile or grade it. `LearningPath` remains a compatibility type for the original path and progress callers. Curriculum content is plain data, independent from provider messages.
- `src/lib/learning-progress.ts` validates bounded version-1 enrollment/completion/activity data under `katalyst.learning.v1`. Completion is an explicit learner action and is not inferred from chats.
- `src/components/assistant-markdown.tsx` renders assistant text through ReactMarkdown and GFM, applies syntax highlighting and safe-link rules, and provides responsive tables and a copy-only code action. It parses the current message value without carrying parser state, so it can accept future streamed partial text. User messages continue using plain text.
- `src/lib/providers/catalog.ts` contains the shared provider IDs, `ModelMetadata` contract, OpenAI's built-in list, and the documented OpenRouter free-router choice. Cloudflare is the deterministic initial hosted default when no valid environment provider or saved browser provider exists.
- `src/lib/providers/discovery.ts` fetches and normalizes Cloudflare, Gemini, and OpenRouter catalogs and calls local Ollama discovery. Cloudflare validates the account-search response envelope, follows at most ten 100-entry pages, preserves exact `@cf/...` IDs, filters explicit non-generation task metadata plus known non-chat metadata hints, and returns raw/compatible/excluded counts with a diagnostic. Gemini compatibility requires `generateContent` and the curated recommendation set is separate from the compatible list. Cloud catalogs use bounded response parsing and a short-lived cache keyed with credential digests (and Cloudflare account ID); Ollama is fetched fresh because installed models can change.
- `src/lib/providers/types.ts` defines the common adapter, request, normalized result/optional usage, abort signal, and provider-error types.
- `src/lib/providers/cloudflare.ts`, `openai.ts`, `gemini.ts`, `openrouter.ts`, and `ollama.ts` isolate each provider's request, response, and error handling. Ollama URL validation and local-host request checks live in its adapter module.
- `src/lib/providers/credentials.ts` resolves environment or transient session credentials (plus Cloudflare account ID) and enforces HTTPS for non-loopback session-key requests.
- `src/app/api/models/route.ts` validates provider selection, passes Cloudflare account/token details only to discovery, rejects public-host Ollama requests, and returns `no-store` catalog responses without secrets.
- `src/app/api/chat/route.ts` bounds request bodies and content, validates the selected provider/model and optional `workspace`/`kat` surface against schemas and the appropriate built-in or dynamic catalog, then invokes the adapter with request cancellation.
- `src/app/api/status/route.ts` returns configured booleans and supported initial defaults. It never returns key values.
- `src/lib/providers/prompt.ts` places project and skill context in the latest user message and keeps trusted provider instructions separate. Per-request instructions include the selected provider, exact model ID, and assistant surface as JSON-encoded route metadata. The OpenRouter free route explicitly does not claim to know which underlying model was selected. Prompts state the app's lack of web, filesystem, external-account, tool, and code-execution capabilities; the UI labels each Kat reply with its own request route instead of the current picker state.
- `src/lib/skills.ts` validates imported skill records, preserves source metadata, and composes bounded workspace context.
- `src/lib/workspace-portability.ts` defines strict versioned JSON backup schemas, credential redaction, conflict-safe merge/replace behavior, and the single-write import transaction.
- `src/lib/workspace-storage.ts` validates the existing local v1 data shape, recognizes supported legacy data, classifies recovery states, salvages valid projects/conversations, and bounds serialized workspace writes.
- `src/lib/account-data.ts` reuses the local workspace, progress, and preference schemas for server account snapshot validation, guest/account merge, hashing, and local mirroring. It does not include AI activity, playground drafts, Kat tutor turns, or provider session keys.
- `src/lib/supabase/client.ts`, `server.ts`, and `src/proxy.ts` provide the browser and cookie-backed server clients and refresh Supabase sessions. The proxy is not an authorization boundary.
- `src/lib/account-server.ts` verifies identity with `auth.getUser()` and checks same-origin mutation requests. `src/app/api/account/` exposes only current-user snapshot read/write, export, and confirmed deletion routes.
- `supabase/migrations/20261110000000_account_persistence.sql` creates user-linked profiles, snapshots, migration markers, RLS, a live-session check, and an atomic revision/migration RPC. `supabase/tests/account_ownership.test.sql` contains pgTAP ownership coverage.

## Product shell, theme, and settings

The shared palette is defined in `src/app/globals.css` through high-contrast Light/Dark/System semantic tokens. Dark mode uses an obsidian canvas, graphite panels, hairline borders, crisp white body text, and sky-blue/indigo accents. Geist and JetBrains Mono provide the interface and technical-label typography. `src/components/brand-mark.tsx` reuses the final user-supplied K mark from `public/brand/katalyst.png` across the interface; rounded PNG variants supply the app icons. The Home pipeline graphic connects all published learning fields. Appearance preferences remain in their existing separate local record; the redesign does not change workspace or learning data schemas.

Settings in `src/components/workspace.tsx` is a keyboard-accessible tabset. It organizes application preferences into distinct categories:
- **Account**: Supabase authentication status, email/password or Google sign-in/out (on the single `/login` page), account snapshot sync, data export, and deletion.
- **Appearance**: Theme selection (System, Light, Dark) and density settings.
- **AI & Models**: Provider selection, model catalog picker, transient BYOK key inputs, and connection status.
- **Usage & Credits**: Real-time shared AI gateway status, active model, remaining credit balance meter, zero-credit BYOK policy notice, and recent AI request activity log.
- **Learning**: Progress reset and learning domain preferences.
- **Workspace**: Versioned backup export and conflict-safe JSON import.
- **Privacy & Security**: Telemetry policies, data handling principles, and local storage controls.
- **Admin**: Isolated gateway configuration controls (model selection, credit weights, monthly quotas, rate limits, kill switch). Rendered conditionally only when the authenticated user's email matches `KATALYST_ADMIN_EMAILS`.

The selected category lives in component state and is preserved when users leave and return to Settings during the current app session. Provider and model menus dismiss on outside pointer input and Escape, and their document listeners exist only while a menu is open.

### Learning Workspace and Splitter Layout (M17.3)

The learning workspace (`src/components/learning-experience.tsx`) features an intentional, focus-first layout:
1. **Default 2-Panel Layout**: Theory / Lesson Guide (50%) on the left and Code Sandbox (50%) on the right.
2. **Optional Kat AI Tutor**: Kat is closed by default to minimize visual distraction and promote independent thinking. Learners can toggle Kat via the "Ask Kat" / "Hide Kat" button in the workspace top bar, opening into a 3-panel layout (Theory 35%, Code 35%, Kat 30%) with draggable and keyboard-accessible splitters. Layout state and Kat visibility are saved to `katalyst.workspace.layout.v1` via `WorkspaceLayout.katOpen`.
3. **Multi-Language Execution Subsystem**: Backed by `src/lib/execution/` with runner adapters:
   - `WasmerCRunner`: Client-side C11 compilation and execution via Wasmer SDK WebAssembly.
   - `PyodidePythonRunner`: Client-side Python 3.12 execution via Pyodide WebAssembly micro-runtime.
   - `RemoteSandboxRunner`: Planned remote container runner for heavy runtimes (Java).
4. **CodeMirror 6 Multi-Language Editor**: `src/components/code-workspace.tsx` provides high-performance, accessible editing with dark graphite surfaces (`#1a1d21`), line numbers, C/C++ and Python stream tokenizers, Run/Stop controls, and responsive stdin/terminal panes.

On desktop viewports, panels are separated by draggable, keyboard-accessible splitter dividers (`role="separator"`, `aria-orientation="vertical"`). Learners can drag splitters or use Left/Right arrow keys (with Home/End to snap). Layout proportions are automatically persisted to `localStorage` under `katalyst.workspace-layout.v1` and restored on subsequent visits.

On smaller screens (<= 1200px), accessible Learn, Code, and Kat tabs toggle panel visibility without unmounting component instances, preserving editor state and execution context across tab switches. Mobile layouts provide horizontal scrolling tabs with sticky-free positioning.

## Catalog and request flow

The browser saves provider and per-provider model IDs in `katalyst.workspace.v1`. Model metadata, Cloudflare account ID, and session credentials are held in component memory; the picker renders at most 150 matches and uses search to narrow larger catalogs. OpenAI uses its existing built-in catalog. Cloudflare discovery calls the documented account-scoped model search endpoint using pages of 100 entries and preserves the returned `@cf/...` identifier, normally from the catalog `name` when present. It does not maintain a model allowlist. Explicit non-text tasks are excluded; entries missing optional task metadata are retained unless known non-chat name/description hints apply. Settings distinguishes an empty raw catalog from a non-empty catalog filtered to zero compatible entries. Gemini discovery follows Google's official paginated model-list API, retaining models that advertise `generateContent`, have a positive output token limit, and do not match known non-text, preview, latest, or retired model families. It marks `gemini-3.8-flash`, `gemini-3.5-flash-lite`, and `gemini-2.5-pro` recommended only when a selected key returns them. OpenRouter discovery requests text input/output models and maps context, supported parameters, namespace, and prompt/completion prices into `ModelMetadata`. Ollama returns only installed models reported by its local tags API. The official `openrouter/free` router is a separate catalog choice and is never an implicit fallback.

The metadata contract stores provider ID, unchanged model ID, name, capabilities, optional context and price, pricing state, discovery source/time, namespace, and whether discovery was key-scoped or access remains unverified. Catalog presence does not imply generation access. Gemini results are listed by the supplied credential, while OpenRouter listing does not verify access. API calls remain the authority for actual model access.

Dynamic cloud catalogs are capped at 3 MB per upstream response and ten pages (Cloudflare pages are 100 entries each), use a 20-second timeout, reject redirects, and cache for five minutes per provider and SHA-256 digest over the credential (plus Cloudflare account ID) with 32 entries maximum. The browser can request a refresh that bypasses the cache. Failed refreshes leave the last successful catalog and selected model in place; a successful refresh that no longer contains the selected model prompts for a new explicit choice. OpenRouter's synthetic free-router choice can be shown without a key, but an inference request still needs a key. Ollama calls `GET /api/tags` on the validated loopback endpoint, applies a 2 MB response limit and an 8-second timeout, returns installed model names/size/parameter/quantization metadata, and does not cache results.

The chat route accepts at most 20 messages, 8,000 characters per message, 24,000 characters of workspace context, 44,000 aggregate message/context characters, and a 192 KB body. Dynamic selections are checked against a fresh/current cached catalog before generation. Adapters return normalized text and optional provider-reported usage. OpenAI, Gemini, and OpenRouter calls use a 45-second timeout; Cloudflare Workers AI uses 60 seconds; local Ollama has a 120-second generation timeout to allow model loading. All requests are non-streaming and reject redirects. No adapter automatically chooses a different model.

Cloudflare sends OpenAI-compatible `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/v1/chat/completions` with bearer authentication and the exact model ID selected from the account catalog; its 60-second request timeout accounts for Workers AI latency. Settings' separate **Test inference** action uses the same route with one minimal user message and is only sent after an explicit click and a listed Cloudflare model selection. OpenAI sends `POST https://api.openai.com/v1/responses`, `store: false`, and a 1,200-token output cap. Gemini uses `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, `x-goog-api-key`, a 1,200-token output cap, and the official contents/systemInstruction shape. OpenRouter uses `POST https://openrouter.ai/api/v1/chat/completions`, bearer authentication, the selected exact model ID, and a 1,200-token output cap. Ollama uses `POST /api/chat` with `stream: false`.

The Ollama address defaults to `http://localhost:11434`; Settings accepts only `localhost`, `127.0.0.1`, or `[::1]` on port 11434, with no credentials, path, query, or fragment. Remote custom endpoints, LAN addresses, redirects, and requests to Ollama from non-loopback KATALYST hosts are rejected. The default `dev` and `start` scripts bind the KATALYST web server to `127.0.0.1`. KATALYST does not set or expose `OLLAMA_HOST`, download models, or provide model management actions.

## Shared AI Gateway and Credit Accounting (M15)

KATALYST routes all shared Cloudflare Workers AI requests through a central authoritative server-side gateway (`src/lib/ai-gateway/gateway.ts`). Users do not need an API key to access AI features with Kat. Administrators configure the designated shared model, model credit weights, monthly user allowances, guest trials, and global safety thresholds.

Requests to shared AI undergo an 11-step pipeline:
1. **Identity & Session Validation**: Verifies either a Supabase cookie session or a server-minted HMAC-SHA256 signed guest cookie (`katalyst_guest_session`).
2. **Authorization & Emergency Controls**: Validates that shared AI is enabled and the global emergency kill switch is not active.
3. **Admin Model Lock**: Resolves the administrator's designated shared model from `ai_system_config` and checks `ai_model_config` for model enablement and credit weights.
4. **Rate Limiting**: Enforces sliding-window request limits (default 15 req/min for authenticated users, 6 req/min for guests).
5. **Input/Output Bounds**: Validates input character limits (44,000 characters) and request byte payload caps (192 KB).
6. **Atomic Credit Reservation**: Atomically reserves estimated credits in PostgreSQL via row-level locks (`SELECT ... FOR UPDATE`), preventing concurrent overspending.
7. **Cloudflare Workers AI Inference**: Invokes the Cloudflare API using server-only credentials (`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`).
8. **Credit Settlement**: Adjusts user or guest balance based on actual provider-reported token usage or conservative character-based estimations (~3.8 characters per token) when token telemetry is omitted by the upstream provider.
9. **Permanent Accounting**: Records the settled transaction in `public.ai_usage_ledger` with reservation linkage, outcome, and estimation flags.
10. **Failure & Cancellation Recovery**: If inference aborts, times out, or fails upstream, the reserved credits are released immediately so learners are never unfairly docked.
11. **Telemetry & Client Headers**: Returns the generated response alongside updated credit balance and quota status.

Authenticated learners receive 1,000 credits per UTC calendar month (first day of month 00:00 UTC to first day of next month 00:00 UTC) without rollover. Unregistered guests receive a 50-credit restricted trial. To mitigate trial-reset abuse from clearing browser storage, guest sessions are cryptographically signed and coupled with salted one-way IP hashing. When quotas are exhausted, structured error payloads (`GUEST_TRIAL_EXHAUSTED`, `MONTHLY_QUOTA_EXHAUSTED`) guide the user to sign in or create an account through the single `/login` page, or select a BYOK provider.

BYOK providers (Gemini, OpenAI, OpenRouter, and local Ollama) bypass shared credit reservation and settlement entirely. BYOK usage consumes zero KATALYST credits and never automatically triggers Cloudflare inference.

Brevo transactional messaging (`src/lib/email/brevo.ts`) operates server-side for welcome notices, low-balance warnings, and quota exhaustion alerts. Brevo calls are non-blocking and fault-tolerant; external email delivery failures never disrupt core authentication or inference requests.

## Credential handling and persistence

`.env.local` provides developer/server credentials through `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, and `OPENROUTER_API_KEY`. `AI_PROVIDER` is the initial provider and defaults to Cloudflare when absent/invalid; an existing saved browser provider choice takes precedence. `AI_MODEL` can select an OpenAI built-in model. Session BYOK values and the session Cloudflare account ID are held only in page memory; the token is sent in `x-katalyst-provider-key`, while the account ID uses `x-katalyst-cloudflare-account-id`. They are never written to localStorage, IndexedDB, chat records, URLs, or server-side persistent storage. The server receives the secret transiently to call the selected provider; dynamic cache keys contain only a SHA-256 digest. Session-key requests require HTTPS except on loopback for local development.

## Account persistence

In guest mode, projects, conversations, imported skills, provider choice, model IDs, and the optional local Ollama address remain in the existing localStorage record. After explicit account migration, the same workspace shape, separate learning progress record, and appearance preferences are mirrored to one RLS-owned JSONB row per Auth user. This is snapshot storage, not per-message relational storage; nested records inherit the owning `user_id`. Session provider credentials never enter the account snapshot. KATALYST does not claim app-level encryption at rest. Persistent BYOK is not implemented.

Account snapshots use the current strict workspace schema, version-1 learning-progress validator, and version-1 preference validator, with a 9 MB aggregate limit. Reads use the user's cookie-backed Supabase session and RLS. Writes go through `save_account_snapshot`, which compares `expectedRevision` atomically and records a guest migration ID in the same transaction when supplied. A stale revision returns a conflict without changing the row. The guest migration marker makes uncertain retries idempotent. The browser keeps local keys and a per-device guest backup, syncing its local mirror only after a user chooses migration/restore. Cross-device updates are accepted automatically only if the local hash still matches the prior synced marker; otherwise the UI asks the user to merge or use the account copy.

`src/proxy.ts` refreshes the PKCE cookie session; every account Route Handler separately verifies the user using Supabase Auth's `getUser()`. The database uses RLS ownership checks and a live `auth.sessions` match for snapshot reads. The session check also blocks a revoked user's otherwise unexpired JWT. Only account deletion uses the server-only service-role key, after deriving the user ID from the verified session. Auth deletion cascades through profile, snapshot, and migration tables. Supabase's project backup retention is managed by the configured project plan and is outside the app's control.

## Provider configuration and discovery

Provider configuration distinguishes credential presence from successful authentication. In-page key drafts are explicitly saved to React memory for the current tab; the save-and-discover action passes that same draft to `/api/models`, preventing a stale closure or older session value from being used. Clearing the session key removes it from page state. Server environment credentials remain available and are resolved server-side according to the provider credential rules. `/api/status` reports only configured booleans and supported initial configuration, never key material.

Each provider card reports credentials, authentication, model catalog, and last inference independently. For Cloudflare, successful discovery is labeled as a catalog request accepted with inference still untested; the separate manual test action reports an actual generation result. Catalog errors include a safe optional error kind without returning upstream payload text or credentials. Gemini discovery checks the upstream status before parsing JSON, so non-JSON authentication failures remain authentication errors, and successful responses with malformed catalog structure are rejected. A failed catalog refresh leaves the last successful catalog and selection intact; after a successful refresh that no longer includes a selected dynamic model, the selection is cleared and the user receives an explicit prompt to select a currently available model. No provider or model fallback is performed.

## Learning domain foundation

The learning catalog composes reusable `LearningSubject`, `LearningCourse` (also exposed under the compatibility name `LearningPath`), `LearningModule`, `LearningLesson`, `LearningObjective`, `LearningExercise`, and `LearningCheckpoint` records. The current published catalog contains one C programming subject and the existing beginner course ID `c-programming-foundations`, with five ordered modules and thirteen ordered lessons. It preserves the original six lesson IDs and their version-1 progress references. The authored data includes learning outcomes, objective references, earlier-lesson prerequisites, explanations, complete C11 examples, differentiated exercises, expected outcomes, optional starter code, and separate self-check questions/answers. Zod plus cross-reference validation checks IDs, subject/objective/exercise links, module and lesson order, prerequisites, text bounds, and balanced matching Markdown fences when the catalog loads. Course selection UI derives from published entries, so draft courses remain hidden. The C course's estimated duration remains `null` until measured; no unsupported estimate is displayed.

`StudentProgress` is currently a local enrollment record with `pathId`, enrollment time, last opened lesson ID, completed lesson IDs/timestamps, and a capped recent activity list. `TopicMastery`, graded `Assessment`, adaptive sequencing, and persisted `TutorSession` are not implemented. Students mark lessons complete themselves. A chat turn cannot change course progress.

Progress lives at `katalyst.learning.v1`, is strict and bounded to 256 KB, validates path/lesson IDs against the current curriculum, and is not written over when the record is corrupt or has an unsupported schema. It remains separate from `katalyst.workspace.v1` and workspace backup schema version 1. An explicit M14 account migration includes this progress record in the account snapshot; account export includes it too. Account merge unions stable path/lesson records without inferring completions.

Kat uses the existing `/api/chat` route, selected provider and model, and session-only credential headers. In an integrated lesson, the same workspace keeps the lesson, editor, and Kat visible together on wide screens; smaller screens use accessible Learn/Code/Kat tabs while preserving the route and component state. When a learner asks Kat, the reference may include course outcomes, module/lesson/objectives/checkpoint/exercise, the current editor source (7,000 chars max), latest diagnostics (2,000 max), and latest output (2,000 max). The learner's question is primary; context is reference material to use when relevant. Tutor context is bounded to 20,000 characters; the client trims older history to 23,000 characters and at most 20 messages to stay within the existing route limits. Lesson/editor/diagnostic/output fields are framed as untrusted reference data. The four visible tutor styles are prompt guidance, not guaranteed behaviors. An explicit unchecked-by-default control can add enabled workspace skills to a separate 3,000-character cap; disabled skills are filtered out, and included or omitted skill names are shown beside the request in page memory. Skill instructions remain untrusted, optional guidance in user-level context, and cannot grant tools or access to secrets.

### Kat Tutor Persistence & Conversation Memory (M16)

Kat conversations are persistent across page refreshes and navigation sessions under `katalyst.tutor.v1` (`src/lib/tutor-storage.ts`). The store manages up to 50 named conversations with up to 100 messages each. Learners can create new conversations, switch between previous discussions via a header selector, clear current history, rename conversations, and delete obsolete threads. When a user signs in, their Kat tutor conversations are mirrored into their PostgreSQL account snapshot and synchronized across devices without leaking conversation history to unauthenticated guests.

This keeps the product domain above the provider layer: curriculum and completion are useful without a model, and switching model providers does not change the path or progress schema. The integrated C playground connects examples to actual experimentation. Editing and running code are local; an explicit Kat code-help action may include the current bounded source, diagnostics, and output in that learner's provider request. A later assessment design can add evaluation and mastery records deliberately without making conversation history the source of truth.

## C playground and Stdin Handling (M16)

The first path's C fenced examples can be opened in the playground. Standalone statements or fragments are wrapped in a small `main` function; examples that already define `main` are carried over as written. The learner edits `main.c`, optionally supplies stdin, and can inspect compiler diagnostics and program output. Source and stdin are saved in a separate versioned `localStorage` record (`katalyst.c.playground.v1`) with 12,000-character and 2,000-character caps. Invalid or over-limit records are ignored. Editing, compiling, and running do not send code to a provider. Kat includes bounded source (7,000 characters), diagnostics (2,000 characters), and output (2,000 characters) only after the learner asks a code-related question or selects a code-help action; these values are framed as untrusted reference data and are not persisted in tutor turns.

When a curriculum example specifies sample input (e.g., interactive `scanf` inputs), the stdin textarea is automatically pre-filled when opened. The playground normalizes CRLF and ensures trailing newlines so line-buffered `scanf` calls receive terminal input correctly. If a program calls `scanf` or `getchar` but stdin is completely blank, the UI warns the learner and requires explicit confirmation to run with empty input (EOF) or switch to the stdin tab to supply inputs.

The app pins `@wasmer/sdk` 0.19.1 and registry package `clang/clang@=0.160000.1`. On first use, the SDK fetches and caches the compiler package in the current browser profile (110,713,421 bytes, about 106 MiB); it is not bundled into the initial app response. Running requires internet for that initial package fetch and browser support for `SharedArrayBuffer`. Next.js sends `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` so the browser can provide cross-origin isolation. The application CSP explicitly permits HTTPS requests to `registry.wasmer.io` for the first-use package fetch. The compiler is invoked in C11 mode and uses the target, linker, and libraries supplied by this package. The compiled guest runs in a Wasmer browser sandbox with networking disabled. Compile time is limited to 15 seconds, execution to 8 seconds, and combined output to 64,000 bytes. The page offers stop during setup, compilation, and execution; a stalled first toolchain setup is aborted after five minutes. This is a focused learning compiler environment, not a promise of native platform APIs, persistent filesystem access, or complete C library compatibility.

The SDK's browser runtime files and license are copied from the installed package into an ignored `public/vendor/wasmer-sdk` folder by `predev` and `prebuild`; those static files must be regenerated after dependency installation. The pinned SDK uses a Modified MIT license: retain the supplied copyright/license notice and Wasmer UI attribution; its added term requires prominent Wasmer attribution for a commercial product/service once it exceeds 1 million monthly active users or US$1 million monthly revenue. Review the copied license in `public/vendor/wasmer-sdk/LICENSE` before redistributing or changing this dependency. Cross-origin isolation affects all app routes and can restrict third-party embedded resources. Deployment proxies must preserve both configured headers.

## Hybrid Compiler Execution Architecture (M16)

To support future multi-language curricula (C, C++, Python, Java, JavaScript, HTML/CSS) and electronics simulation (Falstad, Wokwi, ngspice) without burdening users with monolithic browser downloads, KATALYST introduces a provider-neutral execution layer in `src/lib/execution/`:
- **`ExecutionRegistry`**: Central runner registry decoupling frontends from specific execution engines.
- **Target Preferences**: Runners can be registered for `browser-wasm` (client-side, 0 latency, free hosting) or `remote-sandbox` (ephemeral container, zero client download, full POSIX runtime).
- **Graceful Fallbacks**: If a remote runner is unreachable or unconfigured, execution gracefully falls back to browser execution when available.

See [COMPILER_ARCHITECTURE.md](COMPILER_ARCHITECTURE.md) for the complete benchmark analysis, cost breakdown ($0/mo browser vs. $5-$12/mo container sandboxes), and migration strategy.

## Local storage validation and recovery

The browser key remains `katalyst.workspace.v1`. Existing raw version-1 workspace objects remain the stored format; M5 did not rewrite them into an envelope or migrate them to IndexedDB. The reader validates projects, chats, messages, skills, provider/model IDs, and active conversation references. It supports older raw v1 objects that lack the Ollama model setting and initializes that setting in memory. It also recognizes a local envelope version 1 if encountered, and rejects unknown envelope/schema versions.

Startup distinguishes a missing record from a valid record, partially recoverable record, malformed record, unsupported version, or inaccessible browser storage. A corrupt, unsupported, or unreadable record is not passed to the normal persistence effect. The UI offers original-record download, validated salvage where possible, backup restore, retry after storage access is restored, or a confirmed new-workspace action. The original raw value is downloaded before recovery/replacement. A failed `localStorage.setItem` leaves the previous value in place and shows a storage error. Workspace serialization is capped at 8 MB, though browser localStorage quotas may be lower and vary by browser/profile.

`localStorage` is synchronous and commonly limited to roughly 5 MiB per origin by browsers ([MDN Web Storage](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)). IndexedDB provides asynchronous transactions and is a plausible future backend for larger histories ([MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)), but M5 defers migration: changing storage engines would require dual-read/rollback semantics, cross-tab conflict handling, import atomicity, and recovery tests against real browser implementations. Until that design and representative data measurements exist, KATALYST keeps the existing key and preserves the current data in place.

## Usage and conversation controls

Completed assistant responses keep the selected provider/model and only token/cost fields reported by the upstream response. OpenAI usage maps `input_tokens`/`output_tokens`; Gemini maps `usageMetadata.promptTokenCount`/`candidatesTokenCount`; OpenRouter maps `usage.prompt_tokens`/`completion_tokens` and shows cost only when `usage.cost` is a valid non-negative number; Ollama maps `prompt_eval_count`/`eval_count` and labels them local usage. Missing values remain absent. No cost is inferred for OpenAI, Gemini, or local inference.

Conversation search scans local titles and message text. Copy uses the browser clipboard. Editing a user turn replaces it and removes later turns on send. Regeneration retries the last assistant turn from the existing history. Retry repeats the last failed request with the same provider/model/context. Stop aborts the browser request and passes the abort signal to provider fetches. The current adapter contract returns a complete normalized result, so streaming is not implemented; stopping cannot retract content already received by an upstream service.

Assistant responses from every provider keep their normalized text in conversation storage and are rendered client-side as CommonMark plus GitHub Flavored Markdown. `react-markdown` builds React elements; raw HTML is skipped, URLs are limited to HTTP(S), `mailto:`, and in-page fragments, and Markdown images are omitted. Fenced blocks use `rehype-highlight`, show a language label when the response specifies one, preserve whitespace in a horizontally scrollable region, and offer a clipboard-only action. This presentation is provider-independent and does not execute code or change provider output. See [Security](SECURITY.md#assistant-response-rendering).

## Workspace portability

The application downloads JSON backups locally and does not upload or sync them. Version 1 uses one of three format identifiers: `katalyst-workspace`, `katalyst-project`, or `katalyst-conversation`. Full workspace files contain projects, instructions, conversations/messages, imported skill content and metadata, provider/model preferences, the optional local Ollama address, the active conversation ID, and an ISO export timestamp. Project and conversation exports also include the skill library so applied-skill references and instructions travel with the records. They never include provider status, session keys, environment credentials, request headers, or other component state.

The backup schemas are strict Zod objects: unknown top-level, workspace, project, chat, message, and skill fields are rejected. Supported imports use schema version 1 only; unsupported versions are rejected without writing anything. Future backup versions require an explicit migration path before they can be imported. The existing browser storage key remains `katalyst.workspace.v1`; no cloud or cross-device migration is performed. Limits are 8 MB per JSON file, 100 projects, 500 conversations per project, 1,000 messages per conversation, and 50 skills. Browser localStorage may have a lower quota than the file limit.

Merge is the default. Imported projects are added without replacing current projects. Colliding project/chat IDs are assigned new IDs, and conflicting skill IDs are remapped with message skill references updated. A matching conversation import appends to the existing project without changing its name or instructions; conflicting conversation IDs are remapped. An identical skill ID/name/instruction set reuses the existing skill. Full workspace replacement is a separate UI choice with confirmation; project and conversation files always merge. KATALYST validates and sanitizes the complete backup, builds the next workspace in memory, then calls `localStorage.setItem` once. A failed validation, size check, or storage write leaves the prior workspace value intact.

Exports use an explicit allow-listed workspace shape, omit credential fields, drop metadata entries whose keys identify credentials, and redact common provider tokens, bearer values, query credentials, and labeled API key/password/token values from exported strings. Pattern matching cannot identify every arbitrary secret embedded in prose, so users should review a backup before sharing it. Recognized credential-like content is replaced with a redaction marker.

## Skills and prompt boundaries

Built-in and imported skills use `WorkspaceSkill`: ID, name, description, instruction text, source, enabled state, optional filename/source URL, version, author, declared license, compatibility labels, install date, and frontmatter metadata. Markdown imports are limited to 32 KB with `name` and `description` frontmatter. Up to 20 short metadata values are retained; credential metadata fields are discarded, files are not interpreted as scripts or full Agent Skills packages, and exports use Markdown that imports disabled by default. Control and bidirectional formatting characters are removed, and embedded `<script>` blocks are replaced. Imported text renders escaped in the UI.

Only enabled skills enter `composeWorkspaceContext`. Project context and selected skills share a 24,000-character cap; duplicate instructions after whitespace and case normalization are included once, and instructions that do not fit are omitted. The user message records which skills were included or omitted. Source filenames, source links, metadata, license where provided, and declared compatibility remain visible in the library. The Available tab links to Skill Issue's public catalog for manual review and Markdown import; no documented machine-readable catalog API was found during M4 review, so KATALYST does not scrape it or install entries automatically.

Project and skill text is user-provided, untrusted context. It is JSON-encoded and appended to the latest user message, never placed in OpenAI instructions, Gemini `systemInstruction`, or OpenRouter's fixed system message. The same composition applies across providers. The application does not pass provider keys as context or execute imported code. Prompt boundaries reduce instruction confusion but cannot guarantee model behavior against malicious or irrelevant text.

## Security boundaries

Cloud provider adapters use fixed official HTTPS hosts. Custom OpenAI-compatible endpoints are not implemented because safe arbitrary destinations require DNS resolution and IP pinning against private, link-local, and cloud metadata ranges, plus redirect and outbound destination enforcement. Ollama is the limited local exception: its adapter accepts only explicit loopback hosts on the fixed port, rejects redirects, requires the incoming KATALYST request host to be loopback, and checks that a supplied origin exactly matches the request origin. The default app commands bind to loopback so network clients cannot reach these local inference routes. Do not override that binding or expose port 11434 to the internet. Do not add user-supplied remote URLs by checking only the URL string.

The server sends conversation and selected workspace context to the chosen provider. OpenAI requests set `store: false`; consult provider-specific processing and retention terms. Ollama prompts stay on the KATALYST host and are sent to that machine's local Ollama service. Guest mode is local-first and optional account snapshots are user-scoped. A public deployment still needs inference abuse controls, rate limits, and a clear billing model before it can safely accept visitor prompts against server credentials.

## Product experience and local event data

M8 keeps local product state in independent versioned records. `katalyst.workspace.v1` remains the source for projects, chats, skills, provider/model choices, and optional pinned state; old chats remain valid because `pinned` is optional. Conversation operations are pure data transformations in `src/lib/workspace-actions.ts`. Moving a conversation changes only its project membership. Individual share/export produces a credential-redacted Markdown transcript of the title and visible messages; it does not serialize project instructions, skills, provider settings, or a public URL.

Theme and density are validated in `katalyst.preferences.v1`. AI requests are recorded best-effort in `katalyst.ai-activity.v1`, capped at 500 entries, and contain only request ID, timestamp, provider, model, outcome, and provider-reported input/output token counts. Storage errors never block a model request. No prompts, responses, key material, or estimated costs are recorded. Progress dashboards derive lesson events from `katalyst.learning.v1`, project/conversation summaries from the current workspace, and AI summaries from the bounded activity record. AI activity remains local; after an explicit account choice, workspace, learning progress, and appearance are account-synced as one snapshot, but these remain separate local records. No historical events are inferred before tracking exists.

Settings groups appearance, provider connection/setup, model selection, learning, workspace backup, privacy, and optional Account controls. Authentication forms live only on `/login`; Account settings show account status, sync and migration choices, export, sign-out, and confirmed deletion. When Supabase is not configured, guest use continues and the account panel explains setup. A configured environment key or session key means a provider request can be attempted; it does not establish catalog/inference success. Session provider keys and Cloudflare account IDs stay in component memory.

## Deployment and content architecture

Keep the existing Next.js app as the single application and API boundary. Learning curriculum is provider-independent structured data in `src/lib/learning-curriculum.ts`; learner progress is a separate local record, while browser C compilation is a local WebAssembly capability. Provider calls go from the Next.js server directly to the selected provider. Static lesson reads do not make database or remote catalog requests. The current published thirteen-lesson course remains small enough to ship with the learning client module; the C playground component uses a separate client chunk, and the much larger compiler package remains fetched and cached on demand by the browser.

Add a course by registering its subject/content in `learningCatalog`, validating references and globally unique lesson IDs, then marking it `published`; the UI and version-1 progress domain consume the published course list. Keep the authored data outside presentation components. If course count creates measurable initial-bundle cost, consider per-course JSON/Markdown assets with route-level static generation or cacheable static files. Keep local workspace features operational if external lesson hosting is unavailable. Do not add a content database or make lesson reading dependent on Workers AI. There is no current performance or operational evidence that warrants Cloudflare Pages/Workers migration or R2: the current app needs its Node-compatible Next.js API routes, and R2 would add another storage dependency without large remote course assets. Re-evaluate only with bundle measurements, several curricula, public distribution needs, or asset delivery data that demonstrates a benefit.

The current execution split is:

- Browser: Next.js/React UI, local workspace and learning records, theme, dashboard aggregation, conversation transcript export, CodeMirror, and Wasmer guest execution.
- KATALYST application server: bounded API routes, verified account routes, provider credential resolution, model discovery, request validation, provider adapters, and normalized response handling.
- External services: Supabase Auth/Postgres are used only when account features are configured. Only the selected AI provider receives an inference request; provider catalogs are contacted only when loaded. Ollama stays on the local KATALYST host. The C toolchain is fetched from its pinned registry package on first use and cached by Wasmer in the browser.

## Client performance and request behavior

The lesson's playground components are code-split from routes that do not open them and shown with a small loading state while their chunks load. Wasmer's compiler payload is not bundled and retains its browser-profile cache. The published course catalog currently contains 14 courses; full lesson detail is delivered through the validated lesson endpoint when needed. Provider catalog discovery uses the existing bounded in-memory cache and explicit refresh; changing provider only loads an uncached catalog when credentials are configured. There is no database polling or per-page analytics request. Previously recorded bundle measurements are historical and should not be treated as current; re-measure after major dependency or client-component changes.
